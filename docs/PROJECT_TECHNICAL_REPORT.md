**설계 원칙 세 가지**

1. **멀리 있는 것은 삼각측량으로, 가까이 있는 것은 깊이 카메라로.** 고정 웹캠 3대는 넓은 작업대를 한 번에 보지만 정밀도가 낮고, 손목 D435i는 정밀하지만 시야가 좁다. 역할을 나눴다.
2. **위치가 아니라 속도를 보낸다.** 관절 목표를 던지고 기다리면 도중에 사람이 끼어들어도 멈출 수 없다. 20 Hz로 속도를 스트리밍하고 매 틱마다 경로를 다시 계산한다.
3. **모르면 멈춘다.** 광선이 어긋나면 관측을 버리고, 안전한 경로가 없으면 가지 않는다. 애매한 상황에서 "일단 움직인다"는 선택지는 없앴다.

## 1. 카메라 캘리브레이션과 3D 복원

### 1.1 무엇을 알아야 하는가

카메라 픽셀 $(u,v)$ 하나로는 3D 위치를 알 수 없다. 알 수 있는 것은 **광선(ray)** 하나뿐이다. 두 대 이상이 같은 점을 보면 광선들이 교차하고, 그 교점이 3D 좌표다.

이를 위해 필요한 것:

| 기호 | 이름 | 의미 |
|---|---|---|
| $K$ | 내부 파라미터 | 초점거리 $f_x,f_y$, 주점 $c_x,c_y$ — 렌즈가 3D를 픽셀로 바꾸는 규칙 |
| $\text{dist}$ | 왜곡 계수 | 렌즈가 직선을 휘게 만드는 정도 |
| $T_{base\leftarrow cam}$ | 외부 파라미터 | 카메라가 로봇 좌표계 어디에 어떤 자세로 있는지 (4×4) |

이 값들은 `~/webcam_calibration` 번들에 저장돼 있고, 앱은 `WebcamRig`가 읽어 들인다.

### 1.2 픽셀 → 광선

```python
undistorted = cv2.undistortPoints([[u, v]], K, dist)   # 왜곡 제거 + 정규화
d_cam = [x', y', 1]                                    # 카메라 좌표계 방향
d_base = R_base←cam · d_cam,   o_base = t_base←cam
```

수식으로는 광선 $\mathbf{r}(t) = \mathbf{o} + t\,\hat{\mathbf{d}}$.

### 1.3 광선들의 최소제곱 교점 (핵심 수학)

현실의 광선은 정확히 만나지 않는다. 그래서 **모든 광선에 대한 수직거리 제곱합을 최소화하는 점**을 찾는다.

점 $\mathbf{p}$에서 광선 $(\mathbf{o}_i, \hat{\mathbf{d}}_i)$까지의 수직거리 제곱은

$$\|(I - \hat{\mathbf{d}}_i\hat{\mathbf{d}}_i^{\top})(\mathbf{p} - \mathbf{o}_i)\|^2$$

여기서 $P_i = I - \hat{\mathbf{d}}_i\hat{\mathbf{d}}_i^{\top}$ 는 **광선 방향 성분을 지우는 투영 행렬**이다. 전체 비용 $\sum_i \|P_i(\mathbf{p}-\mathbf{o}_i)\|^2$ 를 $\mathbf{p}$로 미분해 0으로 놓으면 선형 방정식이 된다:

$$\left(\sum_i P_i\right)\mathbf{p} = \sum_i P_i\,\mathbf{o}_i$$

```python
A = Σ (I - d dᵀ);  b = Σ (I - d dᵀ) o
point = lstsq(A, b)
```

### 1.4 "정직도 지표" — 광선 간극 (ray gap)

교점을 구했으면 끝이 아니다. **각 광선에서 그 점까지의 최대 수직거리**를 함께 반환한다.

$$\text{gap} = \max_i \|P_i(\mathbf{p}-\mathbf{o}_i)\|$$

이 값이 크다는 것은 **카메라들이 서로 다른 물체를 보고 있다**는 뜻이다(예: cam0은 해머를, cam1은 다른 해머를). 이때 평균을 내면 존재하지 않는 위치가 나온다.

> **게이트: gap > 40 mm 이면 관측 자체를 버린다** (`DETECT_MAX_RAY_GAP_M = 0.040`)

이 한 줄이 시스템 전체 신뢰성의 근간이다. 오검출이 있어도 "여러 각도에서 일관되게 보이는 것"만 통과한다.

## 2. 물체 검출 — 먼 거리 문제와 해결

### 2.1 문제

기존 YOLO 모델은 **손목 카메라의 근접 뷰**로 학습돼 있었다. C270은 1.3 m 떨어져 있어 해머가 프레임의 몇 %밖에 안 된다. 원본 프레임 그대로 넣으면 **신뢰도 0.05** — 사실상 검출 불가.

### 2.2 해결: 작업영역 크롭 + 업스케일

로봇의 작업 가능 영역(3D 박스)의 **8개 꼭짓점을 각 카메라로 투영**해 2D 경계상자를 만들고, 그 영역만 잘라 최대 3배로 확대한다.

```
WORKSPACE_CORNERS_M = x∈(0.12, 0.78) × y∈(-0.45, 0.45) × z∈(0, 0.25)  [8점]
→ camera.project() → 2D bbox → +20px 여유 → 최대 3배 업스케일 → YOLO
```

결과: 신뢰도 **0.05 → 0.21/0.27/0.33** (카메라별). 물체가 모델이 아는 크기로 돌아온 것이다.

낮은 임계값(0.15)을 쓰되, **광선 간극 게이트가 오검출을 걸러내는** 구조다. "검출은 관대하게, 3D 검증은 엄격하게."

### 2.3 안정화: 중앙값 + 산포 게이트

한 번의 관측을 믿지 않는다.

```
6회 관측 수집 → 중앙값 계산 → 모든 관측이 중앙값에서 40 mm 이내인가?
   아니면 가장 오래된 것 하나 버리고 재시도
```

중앙값을 쓰는 이유는 **이상치 하나가 평균을 끌고 가지 못하게** 하기 위해서다.

### 2.4 시행착오: 유령 목표

> **증상**: 로봇이 존재하지 않는 해머를 향해 작업대 끝으로 기어갔다.
> **원인**: 팔에 매달린 **그리퍼 자신**이 해머로 검출됐다. 3대가 모두 같은 그리퍼를 보니 **광선 간극이 완벽하게 작았다** — 간극 게이트로는 못 잡는다. 그것은 진짜로 하나의 물체였다.
> **해결**: 물리적 사전지식을 추가. 집을 물체는 **테이블 위에** 있다.
> ```python
> DETECT_TARGET_Z_MM = (-30.0, 120.0)   # 이 높이 범위 밖이면 목표가 아님
> ```
> 그리퍼는 z ≈ 226 mm에 있었으므로 즉시 걸러졌다.

**교훈**: 기하학적 일관성만으로는 부족하다. 도메인 지식(공구는 바닥에 놓여 있다)이 마지막 방어선이 된다.

## 3. 장애물 = 사람의 손 — 감지와 모델링

### 3.1 왜 배경차분을 버렸나

처음에는 배경 이미지와의 차이로 침입자를 찾았다. 문제:

- **로봇 팔 자신이 장애물로 검출됨** (팔이 움직이면 배경과 달라진다)
- 팔이 있던 자리에 **유령 잔상**이 남음
- 조명이 바뀌면 전체가 장애물

→ **MediaPipe Hands로 교체.** "사람 손처럼 생긴 것"만 검출하므로 로봇 팔은 원리적으로 장애물이 될 수 없다.

```python
mp.solutions.hands.Hands(
    static_image_mode=False,      # 비디오 모드: 프레임 간 추적 상태 유지
    model_complexity=0,           # 가장 가벼운 모델 (지연 최소화)
    min_tracking_confidence=0.25, # 낮게: C270에서 빠른 손은 모션블러가 심함
)
```

> **카메라마다 별도 인스턴스를 만든 이유**: MediaPipe 추적기는 **하나의 영상 스트림**을 가정한다. 3개 시점을 번갈아 넣으면 손이 카메라 사이를 순간이동한다고 판단해 추적이 무너진다.

### 3.2 손 하나로는 부족하다 — 캡슐 모델

손을 구 하나로 모델링했더니, 로봇이 **주먹만 피하고 팔뚝을 스치며** 지나갔다.

그래서 **캡슐(capsule)** — 선분 + 반지름 — 로 바꿨다:

```
    손목(landmark 0)              팔꿈치 방향 외삽점
         ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━●
         ╰────── 반지름 r ──────╯
   forearm_point = wrist + (wrist - middle_mcp) × 1.6
```

- 축의 한쪽 끝: 손목 랜드마크의 3D 삼각측량
- 다른 쪽 끝: 손등 방향의 반대로 손 크기의 1.6배 외삽 → 팔뚝
- 반지름: 각 카메라에서 본 손 반경(px)을 깊이로 환산해 **평균**

$$r = \text{mean}_i\left(\frac{r_{px,i} \cdot z_i}{f_{x,i}}\right), \quad r \in [40, 130]\,\text{mm}$$

> **최댓값이 아니라 평균인 이유**: 카메라마다 손의 실루엣이 다르게 보인다. 손가락을 그 카메라 쪽으로 편 뷰가 가장 크게 보이는데, 그건 손의 **딱딱한 부피**를 과대평가한 값이다.

### 3.3 등속 칼만 필터 — 반응이 아니라 예측

관측은 위치뿐인데, 회피에 필요한 것은 **어디로 가고 있는가**다.

상태 $\mathbf{x} = [x,y,z,v_x,v_y,v_z]^{\top}$, 등속 모델:

$$F = \begin{bmatrix} I_3 & \Delta t\,I_3 \\ 0 & I_3\end{bmatrix}, \quad
Q = \sigma_a^2 GG^{\top},\ G=\begin{bmatrix}\tfrac{1}{2}\Delta t^2 I_3\\ \Delta t\,I_3\end{bmatrix}$$

$$H = [I_3\ \ 0], \quad K = PH^{\top}(HPH^{\top}+R)^{-1}$$

가속도 잡음 $\sigma_a$를 크게(400 mm/s²) 잡았다. 사람 손은 갑자기 방향을 바꾸므로 **모델을 믿기보다 관측을 빨리 따라가게** 만든 것이다.

### 3.4 시행착오: 0.7초의 공백

> **증상**: 사용자가 "팔이 천천히 움직이면 괜찮은데, 확 움직이면 0.7초쯤 로봇이 멍하다"
> **원인 1**: MediaPipe가 모션블러로 손을 놓친다 → 추적 신뢰도 0.4 → **0.25로 완화**
> **원인 2**: 손을 다시 찾았을 때 위치가 크게 튀면 "다른 물체"로 보고 새 트랙을 만들어 필터가 처음부터 시작
> **해결**: **칼만 예측 위치 기준 게이팅**
> ```
> 예측 위치에서 180 mm 이상 떨어진 관측 → 거부
> 단, 3회 연속 거부되면 트랙을 넘겨준다 (진짜 이동한 경우)
> ```
> **원인 3**: GUI 렌더링이 제어 루프와 같은 스레드 → 스트리밍 중 **15 fps로 제한**

## 4. 경로 계획 — "2 cm 안쪽으로 감싸며 부드럽게"

### 4.1 요구사항 (사용자 요구 그대로)

- 장애물이 없으면 **최적 직선**
- 있으면 **반경 + 2 cm 이내로 붙어서** 부드럽게 우회 (멀리 돌지 말 것)
- **실시간으로 계속 수정**
- **절대 팔 아래로 지나가지 말 것** — "물리학적으로 팔을 통과하지 않으면 갈 수가 없어"

### 4.2 알고리즘: 샘플 투영 + 탄성 밴드

일반적인 RRT/PRM 같은 샘플링 플래너를 쓰지 않았다. 이유는 **매 0.15초마다 다시 계획**해야 하는데, 샘플링 플래너는 실행마다 다른 경로를 내놓아 **경로가 요동치기** 때문이다. 결정론적이고 연속적인 방법이 필요했다.

```
1. 직선을 12 mm 간격으로 샘플링
2. 각 샘플에서 캡슐 축까지의 거리 계산
3. 거리 < (반지름 + 20 mm)인 샘플만, 그 표면 위로 반경 방향 투영
4. 나머지 샘플은 그대로 → 직선 - 감싸기 - 직선
5. 탄성 밴드 평활화 10회 반복:
       p_i ← 0.5·p_i + 0.25·(p_{i-1} + p_{i+1})
   평활화로 안으로 파고든 점은 다시 표면으로 밀어냄
```

이 방식의 성질:
- **최소 편차**: 걸리는 구간만 밀어내므로 필요 이상 돌지 않는다
- **연속성**: 장애물이 조금 움직이면 경로도 조금 움직인다 (요동 없음)
- **비용**: O(샘플 수), 수백 μs — 실시간 재계획 가능

### 4.3 시행착오 ①: 지그재그로 장애물을 관통

> **증상**: 경로가 장애물 안에서 갈지자로 꺾이며 관통
> **원인**: 샘플마다 **독립적으로** 가장 가까운 탈출 방향을 골랐다. 캡슐 왼쪽 샘플은 왼쪽으로, 오른쪽 샘플은 오른쪽으로 밀려나 경로가 축을 가로질렀다.
> **해결**: **우회 방향(side)을 우회 전체에 대해 하나만 결정.** 후보를 우선순위로 두고 첫 번째로 실제 통과하는 것을 선택:
> ```
> natural(가장 얕은 지점의 자연스러운 반경 방향) → over(위) → horizontal(옆) → -horizontal
> ```

### 4.4 시행착오 ②: 위로 피하다 안전영역 위반

> **증상**: 로봇이 위로 올라가다 **protective stop**. 펜던트: "안전영역 위반". z ≈ 434, 439 mm에서 발생.
> **원인**: 컨트롤러에 높이 제한이 설정돼 있었다.
> **해결**: `PLAN_Z_MAX = 400.0` — 모든 계획을 그 아래로 제한. 위로 감싸다 천장에 닿으면 **수평으로 감싸는 모드**로 전환.
>
> 이때 배운 것: **모드를 샘플마다 섞으면 안 된다.** 일부는 반경 방향, 일부는 수평으로 밀면 다시 지그재그가 된다. 우회 전체가 하나의 모드를 쓴다.

### 4.5 시행착오 ③: 팔 아래로 지나가려 함

> **증상**(사용자 스크린샷 2장): 로봇이 사람 팔 **밑으로** 통과하는 경로를 만듦
> **왜 위험한가**: TCP(손끝)만 팔 밑을 통과할 수 있어도 **로봇의 손목과 팔뚝은 TCP 위쪽 공간을 차지한다.** 즉 TCP가 통과해도 로봇 몸통이 사람 팔을 쓸고 지나간다.
> **해결**: `path_passes_under()` — 캡슐 **몸통 아래 각기둥**에 들어가는 경로를 무조건 거부.
> ```python
> t = 축 방향 정규화 위치;  0.05 < t < 0.95 (끝단 캡은 제외)
> if horizontal_distance < radius × 0.75 and z < 투영점_z - 0.3×radius:
>     return True   # 팔 아래 = 금지
> ```
>
> **추가 시행착오**: 처음엔 `horizontal < radius + margin`으로 판정했다. 그러자 **팔을 들어올렸을 때 옆으로 감싸는 정상 경로까지 "아래"로 판정**돼 로봇이 얼어붙었다. 감싸기 거리(radius+20)와 "아래" 판정 폭이 같았기 때문이다. → **radius × 0.75**로 좁혀 팔의 실제 발자국만 금지 구역으로 삼았다.

### 4.6 마지막 수단: 끝단 우회와 "가지 않음"

옆도 위도 막히면(팔이 통로를 가로지르고, 위는 천장 제한) **손끝 바깥이나 팔꿈치 뒤로 도는 경유점**을 만든다. 두 경로 중 짧은 쪽을 택한다.

그것마저 실패하면:

```
"No safe way around your arm - waiting"
```

**로봇은 멈춘다.** 사람의 팔을 통과하거나 아래로 지나가지 않고서는 갈 수 없을 때, 가지 않는 것이 유일한 정답이다.

## 5. 추종 제어 — SpeedL 스트리밍

### 5.1 왜 movel이 아닌가

`movel(목표)`은 **블로킹**이다. 명령을 보내면 로봇이 도착할 때까지 아무것도 못 한다. 도중에 사람이 손을 뻗어도 반응할 수 없다.

`SpeedL`은 **속도 벡터를 스트리밍**한다. 20 Hz로 "지금 이 방향으로 이만큼"을 계속 보낸다. 매 틱 경로를 다시 계산할 수 있다.

### 5.2 캐럿(carrot) 추종

경로 위 **전방 70 mm 지점**을 목표로 삼는다.

$$\mathbf{v} = K_p (\mathbf{c} - \mathbf{p}), \quad \|\mathbf{v}\| \le v_{max}$$

- $K_p = 2.0$ (mm/s per mm), lookahead $= 70$ mm → 개활지 순항속도 $\approx 140$ mm/s
- 상한 $v_{max} = 150$ mm/s

> **시행착오**: 처음 $K_p=1.2$, lookahead $=60$ → 72 mm/s. 사용자 반응: "경로는 즉시 휘는데 로봇이 산책하듯 걷는다. 회피를 무시하는 것처럼 보인다." 계획의 반응성과 **몸의 반응성이 따로 놀면** 사람은 시스템이 고장 났다고 느낀다.

### 5.3 슬루 제한 — 보호정지의 진짜 원인

> **증상**: 재계획 직후 protective stop
> **원인**: 재계획으로 캐럿 방향이 **한 틱 만에 반전**된다. 그 부호 반전을 계단 입력으로 컨트롤러에 주면 순간 가속도가 무한대에 가까워진다.
> **해결**: **명령 속도 자체에 가속도 제한**
> ```python
> APPROACH_SLEW_MM_S2 = 700.0   # 완전 반전을 약 0.4초에 걸쳐 수행
> ```
> 700이라는 값은 타협점이다. 낮추면 부드럽지만 손을 따라가는 것이 눈에 띄게 늦고, 높이면 다시 보호정지 위험.

### 5.4 데드맨과 고착 감지

- **TTL 0.2초**: 모든 속도 명령에 유효시간을 붙인다. 앱이 죽거나 네트워크가 끊기면 **로봇이 0.2초 안에 스스로 멈춘다.**
- **고착 감지**: 15 mm/s 이상을 명령하는데 2.5초 동안 2 mm도 안 움직이면 → 컨트롤러가 듣고 있지 않다는 뜻(보호정지, 서보 오프). 타임아웃까지 죽은 팔에 스트리밍하는 대신 즉시 오류로 전환.

## 6. 6축 자유 손목 (Free-wrist)

기본 동작은 **손끝을 항상 아래로** 유지한다(3축 위치 제어). `--free-wrist`를 켜면 이동 중에 공구가 **진행 방향으로 기울고 장애물에서 멀어지는 쪽으로 기울어진다** — 사람이 물건을 들고 걸을 때와 같다.

### 6.1 원하는 방향 계산

$$\hat{\mathbf{z}}_{desired} = R(\hat{\mathbf{a}}, \theta) \cdot [0,0,-1]^{\top}$$

기울임 벡터는 두 항의 합:
- **운동 방향**: 속도 방향으로 (속도에 비례)
- **장애물 회피**: 캡슐 축에서 자신을 향하는 방향으로 (가까울수록 강함)

기울기 총량은 **목표까지 남은 거리**로 램프된다 — 도착 140 mm 전부터 서서히 수직으로 복귀한다. 목표 지점에서 갑자기 자세를 바꾸면 위치 오차가 생기기 때문이다.

### 6.2 축-각 P 제어

$$\boldsymbol{\omega} = K_p\,\alpha\,\frac{\hat{\mathbf{z}}_{tool} \times \hat{\mathbf{z}}_{desired}}{\|\cdot\|}, \quad \alpha = \arccos(\hat{\mathbf{z}}_{tool}\cdot\hat{\mathbf{z}}_{desired})$$

**롤(공구 축 중심 회전)은 제어하지 않는다.** 두 개의 조준 자유도만 쓴다. 롤을 고정하면 손목 가동범위를 아무 이득 없이 소모한다.

### 6.3 특이점 감쇠

M0609의 J5가 0°에 가까우면 **손목 특이점**이다 — 작은 자세 변화에 관절이 폭주한다. J5 각도가 15~30° 구간에서 각속도 권한을 선형으로 줄이고, 15° 아래에서는 0으로 만든다. 잘라내는 것이 아니라 **페이드**시키는 이유는, 하드 컷은 그 자체로 계단 입력이 되기 때문이다.

## 7. 파지 — 물체 모양에 맞춰 집기

접근이 끝나면 손목 D435i로 정밀 정렬한다. 여기서 세 가지를 결정한다: **어디를(중심), 어느 방향으로(요), 얼마나 깊이(z)**.

### 7.1 어디를 — 바운딩박스 중심의 함정

> **증상**: 해머처럼 **L자 물체**는 바운딩박스 중심이 **허공**이다(머리와 손잡이 사이).
> **해결**: 깊이 마스크의 **무게중심** 사용.
> ```
> 박스 테두리 깊이의 중앙값 = 배경(테이블)
> 배경보다 확실히 가까운 픽셀 = 물체
> 그 픽셀들의 평균 좌표 = 잡을 지점
> ```

### 7.2 어느 방향으로 — 최소면적 사각형

같은 마스크에 `cv2.minAreaRect`를 적용해 **물체의 긴 축**을 구한다. 그리퍼는 긴 축에 **수직**으로 닫혀야 한다(손잡이를 가로질러 물어야 미끄러지지 않는다).

이미지 상의 각도를 base 프레임으로 옮기는 방법: 긴 축 위의 **두 점을 각각 3D로 역투영**해 그 차이 벡터의 방위각을 구한다.

$$\text{yaw} = \text{atan2}(\Delta y, \Delta x) + 90° - \text{FINGER\_AXIS\_HOME}$$

> **좌표계 함정**: 자세 표현이 ZYZ 오일러각이다. base Z축 회전을 **추가**하려면 첫 번째 각도에 더하면 된다 — 회전을 **앞에서 곱하는(pre-multiply)** 것과 같다. 뒤에 곱하면 공구 좌표계 기준이 되어 전혀 다른 결과가 나온다.

### 7.3 얼마나 깊이 — 세 번의 실패

파지 실패가 세 번 연속 발생했고, 원인이 매번 달랐다.

**① 안전 박스가 손을 막았다**
경로 추종용 안전 박스 하한이 z=80 mm였는데, 파지는 그보다 아래로 내려가야 한다. 클리핑 때문에 **63 mm 위에서 그리퍼가 닫혔다**(허공).
→ 파지/놓기는 별도의 하한(`GRASP_Z_FLOOR_MM = -15`)을 쓴다.

**② 바닥 높이 추정이 물체에 오염됐다**
물체 주변 40~70 mm 링에서 바닥 높이를 재는데, **중앙값**을 썼다. 해머는 크기 때문에 링의 절반이 물체였고, 중앙값이 26.6 mm(실제 테이블은 0 근처)로 나왔다.
→ **20 백분위수**로 변경. 물체가 링을 완전히 채우지 않는 한, 아래쪽 20%는 테이블이다.

**③ 캘리브레이션에 +28 mm 편향**
튜토리얼 기본 `T_gripper2camera`로 테이블을 재면 z가 26~32 mm로 나왔다(실제 0).
→ 우리 캘리브레이션 번들의 `T_flange_wrist_depth`(홀드아웃 검증됨)를 드라이버의 depth→color 외부 파라미터와 합성. 결과: 테이블 5~11 mm.

**④ (하드웨어) RG2 안전 래치**
위 문제로 손끝을 테이블 아래로 명령한 적이 있었다. RG2의 **손가락 끝 안전 스위치**가 걸려 **safety circuit 1이 래치**됐다. 그 뒤로는 "닫아라" 명령이 **조용히 무시**된다 — 오류도 없이. 폭 값이 110.3 mm에서 변하지 않는 것으로 발견했다.
→ **툴 전원 재인가**로만 해제. 이후 파지할 때마다 **폭 값을 읽어 로그**한다(28 mm ≈ 물체 있음, 10.7 mm ≈ 빈손).

**교훈**: 로봇 시스템의 실패는 좀처럼 한 가지 원인이 아니다. 매 단계의 **관측 가능한 숫자**(바닥 높이, 파지 z, 그리퍼 폭)를 로그로 남기지 않으면 원인 분리가 불가능하다.

## 8. 사람 손 위로 전달

가장 어려웠던 부분이다. **놓아도 되는 순간**을 판정해야 한다.

### 8.1 실패한 판정 기준들

**① 칼만 속도** — 손을 완전히 멈춰도 비전 지터로 40~80 mm/s가 나온다. 영영 릴리스 안 됨.

**② 위치 이력의 최대 편차** — 0.7초 창에서 최대 이탈을 보니, 스파이크 한 번에 무너진다. 사용자: "가만히 뒀는데도 안 놔. 손이 미세하게 흔들린다고 판단하나봐"

**③ 채택된 방법 — 중앙값 + 80 백분위수**
```
0.7초 창의 손바닥 위치들 → 중앙값 계산
각 점의 중앙값으로부터 거리 → 그 분포의 80 백분위수 < 30 mm 이면 "안정"
```
상위 20%(스파이크)를 무시하되, 진짜 움직임은 잡아낸다.

### 8.2 릴리스가 영원히 반복된 버그

> **증상**: 릴리스 작업이 시작됐다가 취소되기를 무한 반복
> **원인**: 릴리스를 시작하면서 손 추적을 껐는데, 릴리스 작업 스레드가 **손 위치를 다시 읽으려** 했다. 추적이 꺼졌으니 값이 없고 → 실패 → 재시도.
> **해결**: 커밋 시점에 **손바닥 위치의 스냅샷**을 찍고, 릴리스는 그 스냅샷 위로만 내려간다.

**설계 원칙**: 되돌릴 수 없는 동작(릴리스)은 **결정 시점의 값에 고정**한다. 실행 중에 세상을 다시 읽으면 세상이 변해 있다.

|---|---|
| 110 mm | 추적 중 손바닥 위 호버 높이 |

## 9. AR 오버레이 — 계획을 눈에 보이게

### 9.1 왜 이게 공짜인가

웹캠 3대가 **캘리브레이션돼 있다**는 것은, 이 시스템이 이미 **AR 트래킹 리그**라는 뜻이다. base 좌표 3D 점을 `camera.project()`로 넘기면 정확한 픽셀에 떨어진다. 필요한 것은 그리기뿐이었다.

### 9.2 깊이감을 만드는 요소들

| 기법 | 원리 |
|---|---|
| **깊이 리본** | 선 대신 사각형 스트립. 폭 $w \propto 1/z$, 색은 깊이로 보간 |
| **접지 그림자** | 경로를 테이블 평면(z=0)에 투영해 어둡게 합성 — 떠 있음을 인지시키는 핵심 단서 |
| **블룸** | 오버레이를 별도 레이어에 그려 1/4 해상도로 블러 후 가산 합성 |
| **흐르는 대시** | 호길이 기준 위상을 시간에 따라 이동 — "살아있는 계획" |
| **캡슐 셸** | 축을 따라 링 6개 + 세로 스파인 4개. 링 밝기를 깊이로 정규화(앞은 밝게) |

### 9.3 오클루전 — 진짜 AR의 핵심

웹캠에는 깊이 센서가 없지만, **손은 추적 중인 3D 캡슐**이다. 따라서 가려짐을 계산할 수 있다.

카메라 $\mathbf{c}$에서 경로점 $\mathbf{p}$로 가는 선분과 캡슐 축 선분의 **최근접 거리**를 구하고:

$$\text{occluded} = (\text{dist} < r) \wedge (s < 0.97)$$

여기서 $s$는 시선 위 파라미터. $s<1$은 **가리는 물체가 점보다 카메라에 가깝다**는 뜻이다.

가려진 구간은 지우지 않고 **흐린 유령선**으로 그린다 — 완전히 지우면 계획이 어디로 가는지 안 보인다.

### 9.4 성능 — 할당자가 병목이었다

첫 구현은 사분면당 **5.7 ms**(4개면 23 ms). 프로파일링 결과 필터링이 아니라 **매 프레임 임시 버퍼 할당**이 비용이었다.

```python
# 모든 cv2 호출에 dst= 로 사전 할당된 버퍼를 넘김
cv2.resize(self.layer, ..., dst=self._small, ...)
cv2.GaussianBlur(self._small, (0,0), 3.0, dst=self._small_blur)
```

결과: **5.7 → 3.0 ms**. 창 전체 크롬은 블룸을 끄고 폰트만 써서 **0.04 ms**.

## 10. 음성 인터페이스 (JARVIS)

### 10.1 구조

```
마이크 → OpenAI Realtime → 전사 → [웨이크 게이트] → 의도 라우터
                                                    ↓
                              ROBOT_SKILL / ASSEMBLY / CONVERSATION
                                                    ↓
                                     확인 질문 → 로봇 스킬 매니저
                                                    ↓
                                     ROS 토픽 → 로봇 앱 (별도 프로세스)
```

로봇 제어는 **물리적으로 분리된 프로세스**다. LLM이 죽어도 로봇은 자기 상태기계로 동작을 마치고, 로봇이 죽어도 코파일럿은 살아 있다.

### 10.2 웨이크워드가 안 되던 7가지 이유

한국어 STT는 "jarvis"라고 절대 쓰지 않는다. 실제로 잡힌 오인식: **잡이스, 샤비, 잡읍, 차비스**.

1. **ASCII 전용 게이트** → 한국어 표기 별칭 목록 + 발음 유사 정규식
   ```python
   _WAKE_FUZZY = re.compile(r"^[자쟈저짜사샤차하잡][비삐브바뷔이]")  # 첫 토큰 2~3글자
   ```
   "서비스", "자비로운"은 깨우지 않는다(일상어 오작동 방지).
2. **게이트 우회 경로 2개**: 모델이 툴 호출 대신 **직접 응답**하거나 **CLARIFY** 판정하면 검사를 안 거쳤다 → 대기 상태에서는 **모든 음성 턴**을 웨이크 검사로 강제
3. **빈 발화 폐기**: 모델이 툴 인자를 비워 보내면 턴이 통째로 버려졌다 → 전사 결과를 1회성 폴백으로 보관
4. **시스템 기본 마이크가 웹캠 마이크**(로봇 셀을 보는 C270). 작업장 소음이 끊이지 않아 VAD가 문장 끝을 영영 못 찾음 → 프로세스에만 `PULSE_SOURCE` 강제
5. **첫 번째 "내장" 마이크는 빈 헤드셋 잭** (Active Port: not available) → 포트 상태를 확인해 자동 선택
6. **마이크 볼륨 15%** (−48 dB, 사실상 무음) → 스크립트가 100%로 설정
7. **스피커→마이크 피드백**: 자기 음성 응답이 스피커로 나가고 마이크가 되들어 "잠깐만요"를 무한 반복 → 대기 중 재생 차단(`speaker_gate`) + **WebRTC 에코 캔슬레이션**(`module-echo-cancel`)

### 10.3 확인 응답의 모양 판정

"응"만 인식하던 것이 실기에서 계속 막혔다. 열거로는 이길 수 없어서 **모양 기반 규칙**으로 바꿨다.

```
확인 대기 중 & 22자 이하 짧은 대답 일 때:
  부정어(아니/취소/잠깐/나중에) 포함  → 거절
  다른 물체를 지목                    → 새 요청으로 라우팅
  긍정 토큰으로 시작하거나 공손 명령형 → 승인
```

승인 폭을 넓히되 **"멈춰"는 언제나 최우선**이고, 애매하면 진행이 아니라 되묻는다. 잘못 승인하면 사용자가 말로 멈출 수 있지만, 잘못 거절하면 사용자가 같은 말을 반복하게 된다 — 비대칭 비용을 근거로 한 선택이다.

## 11. 데이터셋 파이프라인 — 라벨링 노가다 줄이기

### 11.1 문제

검출기를 개선하려면 데이터가 필요한데, 1,000장에 박스를 직접 그리는 것은 며칠 작업이다.

### 11.2 해결 ①: 기존 모델로 초벌 라벨

낮은 임계값(0.15)으로 전체 추론 → YOLO txt 생성. 사람은 **틀린 것만** 고친다.

### 11.3 해결 ②: 교차뷰 라벨 생성 (이 리그만의 무기)

```
cam0이 검출 (0.8) ┐
                  ├→ 삼각측량 → 3D 위치 확정
cam1이 검출 (0.7) ┘         ↓
cam2는 놓침       ←─ 3D 점을 cam2로 투영 = 정답 박스 자동 생성
```

박스 크기는 물리 크기를 거쳐 환산한다:

$$W_{\text{물체}} = \frac{w_{px} \cdot z}{f_x} \quad\Rightarrow\quad w_{px}' = \frac{W_{\text{물체}} \cdot f_x'}{z'}$$

**검증**: 가상의 물체를 놓고 카메라를 하나씩 가려본 결과 **모서리 오차 0.0 px**. 두 대만 검출되면 생성하지 않는다(삼각측량 불가).

이 방식이 만드는 라벨은 정확히 **모델이 어려워하는 원거리·사각 프레임**이다 — 사람이 가장 그리기 싫어하는 그것.

### 11.4 해결 ③: 기하학적 오검출 필터

낮은 임계값은 기둥·케이블을 "screwdriver"라고 부른다. 리그가 아는 두 사실로 걸러낸다:

1. **공구는 테이블 위에 있다** — 박스 중심의 시선을 테이블 평면과 교차시켜 작업영역 밖이면 의심
2. **진짜 물체는 여러 카메라에 보인다** — 다른 카메라의 같은 클래스 박스와 광선이 만나는지

둘 다 실패하면 **삭제가 아니라 격리**(`suspects.txt`). 진짜 물체가 한 대에만 보이는 경우도 있기 때문이다.

측정 결과: 570개 박스 중 **292개(51%)가 걸러졌다.**

### 11.5 해결 ④: 능동학습 루프

```
라벨 → 학습 → 더 나은 자동라벨 → 검수(줄어듦) → 학습 → ...
```

실측 결과:

| 라운드 | 검수 필요 이미지 | 걸러낸 오검출 |
|---|---|---|
| 1 (기존 모델) | 606 (60%) | 341 |
| 2 | 318 (31%) | 45 |
| 3 | 257 (25%) | 34 |
| 4 | **166 (16%)** | **8** |

라벨 품질이 올라가며 자동 라벨이 정확해지고, 그만큼 사람 일이 줄어든다.

### 11.5.1 평가셋 오염 — 반드시 짚어야 할 함정

라운드마다 학습 로그의 mAP를 비교하면 **틀린 결론**이 나온다.

| 학습 | 로그의 mAP50 | val 객체 수 |
|---|---|---|
| v3 | 0.925 | 394 |
| v5 | 0.859 | 542 |

숫자만 보면 모델이 나빠진 것 같다. 그러나 **val 라벨 자체가 바뀌었다.** 초기 val은 모델이 만든 자동 라벨이었다 — 즉 **모델이 자기 답안으로 자기를 채점**한 것이다. 사람이 검수하며 모델이 놓쳤던 객체 148개를 추가하자, 시험지가 어려워졌다.

**올바른 비교는 같은 시험지로 세 모델을 다시 채점하는 것**이다 (사람 검수 val 542객체):

| | v3 | v4 | **v5** |
|---|---|---|---|
| mAP50 | 0.652 | 0.711 | **0.859** |
| Recall | 0.600 | 0.691 | **0.817** |
| wrench | 0.394 | 0.493 | **0.774** |
| screwdriver_red | 0.503 | 0.590 | **0.765** |
| screwdriver | 0.853 | 0.894 | **0.971** |
| hammer | 0.860 | 0.869 | **0.926** |

모델은 매 라운드 **단조 증가**했다. 특히 **wrench는 두 배**(0.394 → 0.774) — 사람이 검수에서 렌치에 박스를 친 결과가 그대로 반영됐다.

**교훈**: 자동 라벨로 만든 검증셋은 모델의 편향을 그대로 물려받는다. 성능을 주장하려면 **사람이 검증한 고정 시험지**가 필요하고, 시험지를 바꿨다면 **이전 모델을 새 시험지로 다시 채점**해야 한다.

### 11.6 색상 기반 클래스 분할

빨강/검정 손잡이 드라이버와 청록 손잡이 드라이버를 구분해야 했다. 손으로 1,144개를 다시 분류하는 대신 **HSV 색조**로 자동 분할했다.

빨강은 색조 0/180 양끝에 걸치므로 **원형 평균**을 써야 한다:

$$\bar{h} = \frac{1}{2}\arg\left(\sum_j e^{i\cdot 2h_j\pi/180}\right)$$

단순 산술평균을 쓰면 색조 3과 178의 평균이 90(청록)이 된다 — **절대 나와서는 안 되는 답**이다.

결과: 1,144개 중 **1,115개 자동 판정**(엄격 임계 → 완화 임계 2단계).

### 11.7 실패에서 배운 것: 사람의 작업을 지키는 법

> **사고**: 재라벨링이 사용자가 방금 검수한 **49장을 덮어썼다.**
> **원인**: 검수 도구가 진행률을 **종료할 때만** 저장했다. 재라벨링 시점에 "검수 완료" 목록에 없던 작업은 보호 대상에서 빠졌다.
> **해결 3중화**:
> 1. 사진 한 장 넘길 때마다 진행률 **즉시 기록**
> 2. 재라벨링은 검수된 파일을 **열지 않음** (오히려 교차뷰 생성의 신뢰 근거로 재사용)
> 3. 재라벨링 직전 **자동 스냅샷** (최근 10개 보관)

**교훈**: 사람의 시간이 가장 비싼 자원이다. 그것을 다루는 코드는 "저장은 나중에"라는 최적화를 해서는 안 된다.

## 14. 발표에서 강조할 만한 지점

1. **"캘리브레이션은 한 번 하면 계속 배당금을 준다"**
   같은 캘리브레이션이 → 물체 3D 위치 → 장애물 3D 모델 → AR 오버레이 → **데이터셋 자동 라벨링**까지 네 번 쓰였다. 각각을 따로 만들었다면 네 배의 일이었다.

2. **"안전은 기능이 아니라 구조다"**
   데드맨 TTL, 안전 박스, 팔 아래 금지, 광선 간극 게이트, 고착 감지 — 어느 하나도 "안전 모드"라는 별도 기능이 아니다. 정상 경로에 녹아 있어서 끌 수가 없다.

3. **"실패의 원인은 대개 여러 개다"**
   파지 실패 하나에 원인이 네 개(클리핑·통계량·캘리브레이션·하드웨어 래치)였다. 각 단계의 숫자를 로그로 남긴 덕분에 하나씩 분리할 수 있었다.

4. **"사람의 시간을 가장 비싼 자원으로 취급하라"**
   라벨링 노가다를 606 → 166장으로 줄인 것은 알고리즘이 아니라 **순서 설계**(능동학습)와 **기하학 활용**(교차뷰)이었다.

5. **"모르면 멈춘다"**
   가장 자랑할 만한 동작은 로봇이 **가지 않는** 것이다. 사람 팔을 통과하지 않고는 도달할 수 없을 때, 화면에 "No safe way around your arm - waiting"을 띄우고 기다린다.
