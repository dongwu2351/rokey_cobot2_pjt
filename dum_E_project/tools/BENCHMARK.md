# cuRobo 성능 측정 결과 — 결정 게이트

측정 환경: RTX 4060 Laptop (8GB) / CUDA 12.4 / torch 2.6.0+cu124 / cuRobo 0.8.0
로봇: M0609 + RG2 (collision sphere 91개), 장애물 구 5개 + 작업대
측정: 설정마다 **완전히 새 프로세스**, 워밍업 10회 후 30회 측정

## plan_pose 설정별

| max_attempts | enable_graph_attempt | seeds | 중앙값 | p95 | 성공률 |
|---|---|---|---|---|---|
| 1 | 0 | default | 690 ms | 823 | 27/30 |
| **5** | **1** | **default** | **182 ms** | **185** | **27/30** |
| 1 | 1 | default | 279 ms | 364 | 26/30 |
| 5 | 1 | 8 | 534 ms | 552 | 27/30 |

→ **최적: `max_attempts=5, enable_graph_attempt=1`, seeds 기본값. 182ms, p95 185ms.**

## 반직관적이지만 재현된 사실 3가지

1. **그래프 플래너를 켜야 빨라진다.** graph=0 → 690ms, graph=1 → 279ms.
   그래프 플래너가 궤적최적화에 좋은 초기값을 주기 때문. 끄면 trajopt 가 맨바닥에서 갈아서 더 느리다.
2. **max_attempts 를 늘리면 빨라진다.** 1 → 279ms, 5 → 182ms.
   첫 시도를 가볍게 하고 실패할 때만 escalate 하는 구조로 보인다.
   재계획 주기를 올리려고 attempts 를 1로 줄이면 오히려 손해다.
3. **seed 를 늘리면 느려지기만 한다.** 기본값이 이미 튜닝돼 있다. 건드리지 말 것.

## 기타

| 항목 | 값 |
|---|---|
| `update_world` (장애물 갱신) | 0.5 ms — 30Hz 루프에 부담 없음 |
| 장애물 개수 영향 | 거의 없음 (0개 730ms ↔ 20개 701ms) — GPU 병렬화 |
| VRAM | 할당 ~120MB / 예약 300~440MB — YOLO 와 공존 여유 |
| `warmup()` | 11.5s (1회) |
| 위치 오차 | 0.00 mm |
| 성공률 | 90% (실패 3건은 목표가 장애물 안에 생성된 경우) |

## 판정

**182ms → 5.5Hz 재계획.** 0.1 m/s 장애물이 사이클당 1.8cm 이동.

당초 기준(50~150ms 충분 / >200ms 재검토)의 경계선이지만 **진행 가능**하다:

- 안전 감시(시공간 충돌 검사)는 **CPU 에서 30Hz** 로 따로 돈다. cuRobo 가 느려도
  "위험하면 감속·정지"는 항상 동작한다. cuRobo 는 "더 나은 경로"만 만들면 된다.
- MoveIt(OMPL + 시간파라미터화)은 0.5~1Hz 수준이므로 **여전히 5~10배 빠르다.**
- CP9(움직이는 통)는 planner 가 아니라 D455 Visual Servo 로 풀기로 했으므로
  고주기 재계획 요구가 완화됐다.

## 남은 최적화 여지

- `plan_cspace` (관절공간 목표) 는 IK 를 건너뛰므로 더 빠를 수 있다.
  목표가 안 바뀌는 연속 재계획에서는 이쪽이 맞을 수 있다.
- 직전 궤적을 seed 로 넣는 warm start (연속성 확보 + 속도) — 미검증.

## 함정 기록

- **작업대를 로봇 베이스 밑까지 깔면 안 된다.** `base_link` 구(z 최저 −0.095)와
  충돌해서 시작 자세부터 불가능 판정이 나고 `plan_pose` 가 통째로 `None` 을 반환한다.
  실제 로봇은 작업대에 고정돼 있으므로 그 접촉은 충돌이 아니다.
  → 작업대를 로봇 앞쪽으로만 두거나 base_link 충돌을 따로 처리할 것.
- **한 프로세스에서 planner 를 여러 번 생성/파괴하면 측정이 오염된다.**
  `destroy()` 후에도 VRAM 예약이 292→438MB 로 계속 늘었고, 뒤에 만든 planner 일수록
  느려지고 성공률이 떨어졌다(90→67→27%). 설정 비교는 프로세스를 분리할 것.

# ⚠️ 위 수치는 무효 — 구 장애물이 무시된 상태에서 측정됨

## 원인

`cuRobo` 의 충돌월드는 **cuboid / mesh / voxel 만** 받는다 (`collision_scene.py:98-100`).
`Sphere` 는 충돌 프리미티브가 아니다 — `SceneData` 에 `has_cuboids/has_meshes/has_voxels`
는 있어도 `has_spheres` 는 없다.

```python
# 잘못됨 — 구 장애물이 조용히 전부 사라진다. 에러도 경고도 없다.
Scene(sphere=[Sphere(...)])
collision_cache={"obb": 32, "sphere": 64}     # "sphere" 라는 캐시 키는 존재하지 않음

# 올바름
Scene(sphere=[Sphere(...)]).get_mesh_world()   # 또는 .get_obb_world()
collision_cache={"cuboid": 32, "mesh": 64}
```

## 확인 실험

로봇을 통째로 감싸는 반지름 0.30m 구를 홈 TCP 에 놓고 계획을 시도:

| 씬 | 결과 |
|---|---|
| `Scene(sphere=...)` 그대로 | **계획 성공** (구가 무시됨) |
| `.get_mesh_world()` | 계획 실패 (구 인식 ✓) |
| `.get_obb_world()` | 계획 실패 (구 인식 ✓) |

## 경로 검증 (verify_path_clearance.py)

장애물 벽 너머로 가는 궤적의 로봇 구 91개 vs 장애물 최소거리:

| | 최소여유 | 궤적 길이 |
|---|---|---|
| 수정 전 | **−100.7 mm** (파고듦) | 61점 |
| 수정 후 | **+8.1 mm** | 141점 (실제로 우회) |

## 교훈

- **`success=True` 는 "충돌 없음"을 보장하지 않는다.** 목표 도달만 뜻한다.
  (`feasible`, `interpolated_metrics` 필드는 존재하지만 채워지지 않는다.)
- 장애물이 인식되는지 반드시 **의도적으로 충돌하는 씬**으로 검증할 것.
  거대 장애물을 놓고 "계획이 실패하는지" 보는 게 가장 확실하다.
- 경로 검증은 `verify_path_clearance.py` 로 상시 확인.

# 재측정 (구 장애물이 실제로 인식되는 상태)

| | plan_pose 중앙값 |
|---|---|
| 구 장애물 무시됨 (버그) | 182 ms |
| **메시로 변환, 실제 인식** | **555 ms** |

**3배 느려졌다.** 앞의 182ms 는 사실상 "장애물 없는 씬"을 잰 것이었다.

## 555ms 가 의미하는 것

```
555ms -> 1.8Hz 재계획
```

당초 기준(>200ms 재검토)을 넘었다. **연속 재계획으로 동적 장애물을 부드럽게
피하는 그림은 이 숫자로는 약하다.** CP8 은 "Hold -> 재계획" 쪽에 가까워진다.

다만 아키텍처 전제는 유지된다:
- 안전 감시(시공간 충돌 검사)는 **CPU 30Hz** 로 독립적으로 돈다.
  cuRobo 가 느려도 "위험하면 감속·정지"는 항상 동작한다.
- MoveIt(OMPL + 시간파라미터화) 대비로는 여전히 빠르다.

## 아직 안 해본 최적화 (우선순위 순)

1. **`get_obb_world()` vs `get_mesh_world()`** — 구를 박스로 근사하면 충돌 계산이
   훨씬 싸다. 부피가 커지는 대신 속도를 얻는다. **제일 큰 손잡이일 가능성이 높다.**
2. `plan_cspace` (관절공간 목표) — IK 단계를 건너뛴다.
3. 직전 궤적을 seed 로 넣는 warm start.
4. 장애물 개수별 재측정 (앞의 "개수 영향 없음" 결과도 무효다).

## 정적 테스트 설정 (검증됨)

장애물 1개 `[0.55, 0, 0.20] r=0.08`, 홈 여유 62.2mm.
목표 4개 중 3개 계획 성공, **경로 여유 +9.7~9.9mm** (실제로 우회함).

`x < 0.55` 에 장애물을 두면 홈 자세의 그리퍼(x≈0.37, z 0.19~0.42)와 겹쳐
시작부터 불가능해진다.

# 씬 표현 방식이 성능을 6배 좌우한다

장애물 구 3개 + 바닥 판 4장, M0609, RTX 4060:

| 씬 구성 | warmup | plan_pose | 성공 |
|---|---|---|---|
| `Scene(cuboid=바닥, sphere=구).get_mesh_world()` | 96.6 s | 2104 ms | 12/12 |
| 바닥은 cuboid, 구만 mesh 로 변환 | 31.5 s | 747 ms | 12/12 |
| **전부 cuboid (구를 `get_obb_world()`)** | **18.5 s** | **340 ms** | **12/12** |

## 핵심

`get_mesh_world()` 는 **씬 전체**를 메시로 바꾼다. 바닥 판까지 메시가 되면서
warmup 이 96초, 계획이 2초까지 늘어났다. 바닥은 cuboid 로 두고 구만 변환해야 한다.

더 나아가 구를 `get_obb_world()` 로 외접 박스로 바꾸면 340ms 까지 떨어진다.
성공률은 세 방식 모두 동일했다.

**대가**: 구를 외접 정육면체로 바꾸면 모서리가 반지름의 0.73배만큼 더 튀어나온다
(r=0.08 이면 5.8cm). 장애물은 어차피 인식오차·예측오차·반응시간을 더해 부풀려
쓰는 값이라 이 보수성은 감수할 만하다. 좁은 틈을 지나야 하는 상황에서만 mesh 로.

**시각화 주의**: obb 모드에서 화면에 구를 그리면 "보이는 것과 피하는 것"이 달라진다.
데모는 obb 모드일 때 박스를 그린다.

## 갱신된 판정

```
340 ms -> 약 3Hz 재계획
```

555ms/1.8Hz 에서 340ms/3Hz 로 개선. CP8(동적 회피)에 실질적으로 쓸 만한 수준이다.

# 실시간 성능 — 원인과 수치 (최종)

## 승인→도착 시간의 변천

| 시점 | 시간 | 원인 |
|---|---|---|
| 초기 | 34.8 s | 제어 틱마다 Scene 재생성 + 월드 재업로드 |
| 부분 최적화 | 26~32 s | FK 호출 축소, floor 캐시 |
| **pose-only 갱신** | **2.0~9.3 s (평균 5.4)** | `update_obstacle_pose()` 로 전환 |

궤적 자체가 2.4초 분량이므로 현재가 정상 범위다.

## 핵심 병목: 씬 재생성 96ms

```python
Scene(sphere=[...]).get_obb_world()   # 96 ms  (trimesh 변환)
```

제어 틱(50Hz = 20ms)에서 이걸 매번 하면 애초에 불가능하다. 실제로 ~5Hz 로 돌았다.

**해법**: 장애물은 위치만 바뀌므로 씬을 다시 만들 이유가 없다.
```python
solver.scene_collision_checker.update_obstacle_pose(name, Pose.from_list([...]))
```

**부작용 주의**: `update_obstacle_pose` 는 **위치만** 바꾼다. 반경은 못 바꾼다.
칼만 불확실성으로 반경을 키우는 설계와 양립하지 않는다. 초기 공분산이 크면
반경이 0.66m 로 굳어 모든 경로가 막힌다. → 반경은 상수, 위치만 예측값으로.

## ★ MPC 는 MPPI 가 아니라 L-BFGS 다

```
curobo/content/configs/task/mpc/lbfgs_mpc.yml :  solver_type: "lbfgs"
mpc/ 폴더에 MPPI 설정 자체가 없음
MPPI 는 trajopt/particle_trajopt.yml 에만 존재 (solver_type: mppi)
```

**경사하강이므로 지역 최소점에 빠지는 것이 구조적으로 필연**이다
(측정: 목표 370mm 에서 254mm 까지 가고 정체).

대응:
1. `MPCSolver.update_seed_trajectory(traj)` 로 전역 경로를 시드로 주입
   (현재는 `update_goal_state()` 로 lookahead 한 점만 주고 있어 = 관절공간 Pure Pursuit.
    MPC 는 그 점까지 어떻게 우회할지 모른다)
2. `mpc/particle_mpc.yml` 을 만들어 `["particle_mpc", "lbfgs_mpc"]` 순차 파이프라인 구성
   → MPPI 탐색 + L-BFGS 정제

## 스레드 / CUDA graph 제약

`use_cuda_graph=True` 인 cuRobo 인스턴스가 여럿이면 **반드시 한 스레드에서 순차 호출**해야 한다.
CUDA graph 캡처 중에는 다른 스레드의 CUDA 연산이 하나라도 끼면 깨진다
— 텐서 생성, `.cpu()` 전송까지 포함이라 수동 락으로는 빈틈을 못 막는다.

**해법**: cuRobo 를 쓰는 콜백을 같은 `MutuallyExclusiveCallbackGroup` 에 넣는다.
단, 고빈도 타이머가 저빈도 타이머를 굶기지 않도록 고빈도 쪽에서 조기 반환할 것.

칼만/시각화는 순수 numpy 라 별도 그룹에 두면 GPU 가 막혀도 계속 돈다.

# ★ 경로가 4.7배로 길어진 진짜 원인 — 손목 분기(wrist branch)

## 증상
목표 `[0.60, -0.28, 0.15]` (y 로 크게 벌어진 지점) 로 계획하면 TCP 가 거대한
원호를 그리며 직선거리의 **4.7배** 경로가 나온다. 화면상 명백히 비효율적이다.

## 원인
```
HOME   J5 = + 90°
목표   J5 = -106°     <- 손목 분기가 반대
```
TCP 는 플랜지에서 238mm 떨어져 있다. 손목이 180도 뒤집히는 동안 TCP 가
큰 원호를 그린다. **J5 를 +0.2~2.09 로 제한하면 계획 자체가 실패한다**
= 그 지점에는 홈과 같은 분기의 IK 해가 존재하지 않는다.

## 시도했다가 안 된 것들 (전부 4.4~4.7배에서 변화 없음)

| 시도 | 결과 |
|---|---|
| trajopt seed 4 → 12 → 24 → 48 | 4.7x 고정, 시간만 463ms → 6742ms |
| 그래프 플래너 끄기 (`enable_graph_attempt=0`) | 4.4x, 성공률 5/5 → 2/5 |
| `null_space_weight` 0.3 → 10.0 | J4 = -179.8° 고정 |
| 툴 자기축 회전 12방향 (-180°~180°) | 전부 4.4~4.7x |
| 로봇 가까이 경유점 삽입 | 1.74m → 1.93m (오히려 악화) |
| 관절공간 직선 보간 | -86.6mm 충돌 (우회 자체는 실제로 필요) |

48개 seed 가 소수점까지 같은 답에 수렴한 것이 결정적 단서였다 —
"여러 후보 중 나쁜 걸 골랐다"가 아니라 "그 답밖에 없다"는 뜻이다.

## 해결 — 작업 지점을 바꾼다

```
장애물 [0.55, 0, 0.12] r=0.07   (작업대 위 물체)
앞 [0.40,0,0.12]  <->  뒤 [0.70,0,0.12]

앞->뒤   직선 0.300  경로 0.444 = 1.5x   최고 z 0.259
뒤->앞   직선 0.299  경로 0.445 = 1.5x
J5 = 80~116°   <- 손목 분기 유지
```

y 로 크게 벌리지 않고 앞뒤로 왕복하면 손목 분기가 유지되어 **4.7x -> 1.5x**.
들어올려 넘어가는 자연스러운 동작이 나오고, Pick&Place 의 실제 모양과도 맞는다.

## 실기에 그대로 적용되는 교훈

> **작업 지점을 정할 때 "도달 가능한가" 만 보면 안 된다.
> "지금 자세와 같은 손목 분기인가" 도 봐야 한다.**

분기가 다르면 로봇이 180도 뒤집히며 TCP 가 크게 휘둘린다. 사람 옆에서는 위험하다.
작업 영역을 미리 스캔해 "홈과 같은 분기로 도달 가능한 영역" 을 확인해 둘 것.
`path_probe_node.py` 가 그 도구다 (슬라이더로 자세를 바꾸며 우회 배율을 실시간 표시).

# 좌표 당기기 + 이탈 판정 수정 (최종 배치)

## 1. 좌표가 M0609 리치 한계였다

```
이전 뒤 TCP(0.70, 0.12) -> 플랜지 z=0.358, 베이스까지 0.786m   한계 근접
새   앞 TCP(0.33, 0.10) -> 플랜지 z=0.338, 베이스까지 0.472m   여유
새   뒤 TCP(0.60, 0.10) -> 플랜지 z=0.338, 베이스까지 0.689m   여유
```
TCP 좌표만 보면 0.70 이 리치(0.9m) 안이라 착각하기 쉽다.
**TCP 는 플랜지에서 238mm 앞이므로 플랜지 위치로 따져야 한다.**

최종: 장애물 `[0.48,0,0.10] r=0.05`, 앞 `[0.33,0,0.10]` <-> 뒤 `[0.60,0,0.10]`,
동적 장애물 `x=0.48, z=0.24, 진폭 0.22, r=0.05`.
동적 장애물까지 포함해 2.4x (장애물 하나만이면 1.5x).

## 2. 이탈 판정이 항상 즉시 중단으로 빠지고 있었다

```python
self._resync_count = getattr(self, "_resync_count", 0) + 1   # 세션 전체 누적
if self._resync_count % 4 != 0: 재시드; return
중단
```

버그 두 개가 겹쳐 있었다.

1. **카운터가 세션 전체 누적** — 실행마다 초기화되지 않아 `% 4` 가 아무 때나 걸린다.
   "3번 시도 후 포기" 가 아니라 "누적 4의 배수번째에 포기" 였다.
2. **재시드 효과를 기다리지 않는다** — 재시드는 `optimize_action_sequence()` 때문에
   87ms 걸린다. 제어 틱은 20ms(50Hz). 다음 틱에 효과가 나타날 수가 없다.
   그래서 "재시드 -> 아직 그대로 -> 중단" 으로 **항상** 즉시 중단됐다.

수정:
- 이탈이 **연속**일 때만 센다 (`dev <= MAX` 면 리셋). 한 번 붙었다 떨어지는 건 무시.
- 재시드 후 `GRACE_TICKS=30` (0.6초) 유예. 그 동안은 세지 않는다.
- `RESYNC_TRIES=3` 회 연속 실패해야 중단.

## 3. 결과 (150초, moving=true, n_static=1, auto_approve=2.0)

| | 도착 | 재시드 | 중단 | 경로없음 |
|---|---|---|---|---|
| 수정 전 | 8 | 9 | **9** | 16 |
| 수정 후 | **12** | 12 | **2** | 12 |

도착 오차는 21~29mm 로 일정. 재시드 12회 중 10회가 복구에 성공했다
= A(시드 주입) 방식이 실제로 작동한다는 직접 증거.

## 교훈

> MPC 가 장애물을 피하려 휘는 것은 **정상**이고 우리가 원하는 동작이다.
> 이탈은 그 휨이 **되돌아오지 못할 때만** 문제다.
> 순간값으로 판정하면 정상 회피를 실패로 오인한다.

# 예측 구간(PREDICT_T)은 근거를 재서 정해야 한다

## 증상
주황 구가 화면에서 크다. 줄이려고 보니 크기가 `실제 반경 + 예측오차 여유` 인데
그 여유값이 맞는지 아무도 확인한 적이 없었다.

## 측정 — 등속 칼만의 예측오차 (물체가 3초마다 방향 전환)

| 예측구간 | 평균오차 | 95%오차 |
|---|---|---|
| 0.0초 | 14mm | 33mm |
| 0.2초 | 26mm | 69mm |
| 0.3초 | 33mm | 88mm |
| 0.8초 | **74mm** | **192mm** |

이전 설정은 `PREDICT_T=0.8, PREDICT_MARGIN=0.035` 였다.
**필요 192mm 인데 여유 35mm** = 예측 위치를 믿고 비켜갔는데 실제로는 딴 데 있었다.
등속 모델은 방향 전환을 예측할 수 없으므로 멀리 볼수록 급격히 나빠진다.

## 얼마나 앞을 봐야 하는가

"로봇이 실제로 비켜나는 데 걸리는 시간" 이다.
그건 MPC 지평 = `MPC_HORIZON(16) x action_dt(0.02) = 0.32초`.
그보다 먼 미래를 예측해봐야 쓸 데가 없고 오차만 커진다. -> `PREDICT_T = 0.3`

## 적용

```
이전: R_MOVER 50mm + 여유 35mm = 85mm (화면 지름 170mm), 예측 0.8초
이후: R_MOVER 25mm + 여유 35mm = 60mm (화면 지름 120mm), 예측 0.3초
```

## 결과 (150초, moving=true, n_static=1)

| | 도착 | 재시드 | 중단 | 경로없음 |
|---|---|---|---|---|
| 이전 | 12 | 12 | 2 | 12 |
| 이후 | 10 | **4** | **0** | **3** |

경로없음 12->3. 로봇이 막혀 서 있는 시간이 크게 줄었다.

## 남아있는 것 (의도적)
여유 35mm 는 0.3초 기준 **평균**오차이지 95%(88mm)를 덮지 않는다.
안전은 주로 50Hz 재계획에서 나오지 이 상수에서 나오는 게 아니다.
꼬리까지 덮으려면 `PREDICT_MARGIN = 0.09`.

## 교훈
> 예측 지평은 "길수록 좋다" 가 아니다.
> **모델이 유효한 구간** 과 **로봇의 반응 시간** 중 짧은 쪽에 맞춘다.
> 등속 모델로 방향 전환하는 물체를 0.8초 앞까지 보는 건 예측이 아니라 추측이다.

# pose_picker — 시작·목표를 직접 집어서 시험하는 도구

`ros2 launch pose_picker.launch.py`

RViz 에서 파랑(시작)/초록(목표) 마커를 끌면 그 조합으로 계획해서 경로를 그린다.
6-DOF 라 위치뿐 아니라 자세도 돌려볼 수 있다. 마커 대신 좌표로도 지정 가능:

```
ros2 topic pub --once /curobo/set_goal geometry_msgs/msg/Point "{x: 0.5, y: 0.1, z: 0.2}"
ros2 topic pub --once /curobo/swap std_msgs/msg/Empty {}    # 시작<->목표
ros2 topic pub --once /curobo/play std_msgs/msg/Empty {}    # 경로 따라 재생
```

지금까지 우리를 물먹인 세 가지를 자동으로 판정한다.

1. **도달 가능성 — 플랜지 기준으로 따진다.** TCP 좌표로 보면 리치 안처럼 보인다.
2. **손목 분기** — 시작/목표 J5 부호가 다르면 경고.
3. **우회 배율** — 3배 넘으면 경고.

## 이 도구로 손목 분기 가설이 다시 확인됐다

같은 목표 `[0.60,-0.28,0.15]` 인데:

```
HOME(J5=+90°)      에서 출발 -> 4.7배   (J5 -106°, 분기 반대)
[0.33,0,0.10](J5=+77°) 에서 출발 -> 1.1배   (J5 +106°, 분기 같음)
```

**목표가 나쁜 게 아니라 시작-목표 조합이 나빴다.** 같은 지점도 어디서 출발하느냐에
따라 4.7배가 되기도 1.1배가 되기도 한다. 작업 순서를 짤 때 분기를 봐야 하는 이유다.

측정: 계획 340~373ms, 재계획 2Hz.
